# AWS-AccessBridge — Backend Data (D1/DAO Layer)

Scope: `packages/backend-data/**`. Parent index: `../../AGENTS.md`.

All D1 access via DAOs extending `dao/BaseDAO.ts` (`BaseDAO` — `ctor(database: D1Queryable)`, `withRetry()`, `deleteOrphanedRows()`; `EncryptedDAO` — adds `encryptionKeys` (an ordered chain: own key first, legacy fallback after) for encrypted rows, e.g. `CredentialsDAO`): `CredentialsDAO`, `AssumableRolesDAO` (+ `AssumableRolesQueries` shared SQL fragments + `AssumableRolesMapper.mapRowsToAssumableMap` pure mapper), `AwsAccountsDAO`, `RoleConfigsDAO`, `UserMetadataDAO`, `UserEmailDAO`, `UserFavoriteAccountsDAO`, `UserAccessTokenDAO`, `AuditLogDAO`, `CostDataDAO`, `DataCollectionConfigDAO`, `SpendAlertDAO`, `ResourceInventoryDAO`, `CredentialCacheConfigDAO`, `CredentialsCacheDAO` (KV), `BackgroundTaskRunDAO`, `TeamsDAO`, `TeamMembersDAO`, `TeamAccountsDAO`; `IKeyValueDAO` KV contract (`get`/`put`/`delete` all namespace the key — `delete` must too); `crypto/` (`aes-gcm`, `hmac` for AES-GCM credential encryption + internal HMAC signing — `encryptData` deliberately takes no caller-supplied IV, see below); `constants/d1/` (`D1_SESSION_CONSTRAINT_FIRST_UNCONSTRAINED` — the only session constraint in use; `first-primary` was declared but never selected, since a route that writes through its session and reads back needs the session writable); `constants/kv/` namespaces/TTL/value-type.

**User identity (`migrations/0032_user_identity.sql`)**: `user_metadata.user_email` is the frozen **anchor** — never updated, still the primary key, and still the target of live foreign keys from `assumable_roles`, `user_favorite_accounts` and `user_access_tokens` (the last `ON DELETE CASCADE`). D1 honours neither `PRAGMA foreign_keys = off` nor `PRAGMA legacy_alter_table = on`, and `defer_foreign_keys` does not suppress `ON DELETE CASCADE`, so those references cannot be repointed without losing rows; the migration is purely additive for that reason. `user_metadata.id` (`usr_<hex>`) is the stable account key; `current_email` is the mutable sign-in address; `user_emails` is the address registry (`is_verified = 1` may authenticate). So a `*_email`/`created_by` column is written with the **anchor** (it is the FK target and, for `assumable_roles`/`user_favorite_accounts`/`team_members`, half of a primary key), while identity-keyed reads and writes go through `user_id`. `0032` assigns `current_email` only where the lowercased address is unambiguous, so a live database holding both `Alice@x.com` and `alice@x.com` is neither merged (a privilege escalation) nor failed (a unique-index violation); those rows keep `current_email IS NULL` and resolve via the anchor. User-keyed DAO methods therefore take an owner object — `AssumableRoleOwner` (`{userId, anchorEmail}`) or `TeamMemberOwner` — not a bare address, and the shared predicate is `ownerClause(alias)` = `(alias.user_id = ? OR (alias.user_id IS NULL AND alias.user_email = ?))`; the `IS NULL` guard is load-bearing, since without it an address an account has moved away from would also match a different account's row. `UserMetadataDAO.ensureUserEmailExists` stamps `id`/`current_email` on insert — a row created after 0032 is never backfilled again, so provisioning without them leaves a permanently unresolvable account; `getOrCreateFederationUsername` calls it first and then writes the username with an `UPDATE`, because D1 does not enforce foreign keys by default, so an `assumable_roles` row can already exist with no metadata row and this path becomes that account's first writer.

**Credential encryption**: every encrypted field gets its own random 96-bit AES-GCM IV, stored in its own column (`salt`, `salt_secret_access_key`, `salt_session_token`). Never reuse an IV across fields under one key — it leaks the XOR of the plaintexts and enables tag forgery. `encryptData` therefore accepts no IV argument. Decryption takes a *chain* of keys, not one: `decryptDataWithKeys`/`decryptDataField` walk it in preference order, which is what makes the per-feature key split non-breaking — a wrong key fails GCM's tag check rather than returning garbage, so trying the next one is safe. `decryptDataField` answers `undefined` for an absent column (a relationship-only `credentials` row legitimately has none) but throws when an envelope is present and unreadable; `decryptDataTolerant` returns `undefined` for both, and is only for the disposable KV cache. Rows written before `migrations/0031_distinct_credential_ivs.sql` carry only `salt`; reads fall back to it (`CredentialsDAO.resolveIv`, and the same fallback in `CredentialsCacheDAO`), so old rows keep working and are upgraded on their next write.

`utils/` (`D1Utils.executeD1WithRetry` + `assertD1Success`, `D1ErrorClassifier.isD1ErrorRetryable` + `isMissingSchemaError` (missing-table/column only — never swallow a constraint violation or timeout), `D1SessionUtil` (`D1Queryable`, `createD1SessionEnv`), `LIKEUtil` (`contains`/`escape`/`escapeClause` — LIKE metacharacter escaping for search terms)).

**D1 write discipline**: D1 resolves a failed statement with `{success: false}` rather than throwing, so **every** write goes through `this.withRetry(...)` (or `assertD1Success`), which retries a retryable error and otherwise throws `DatabaseError`. A write that skips the check reports success for a row that does not exist — that is how `TeamsDAO.createTeam` returned a `teamId` resolving to nothing, and how `AuditLogDAO.deleteOlderThanBatch` made `AbstractPruningTask` log "Pruned 0 rows" and exit successfully while retention silently stopped. The 7 `deleteOrphaned()` implementations share `BaseDAO.deleteOrphanedRows` and the `ORPHANED_BY_ASSUMABLE_ROLES` predicate rather than retyping inline SQL.

**The 0032 owner predicate has one definition.** `AssumableRolesQueries.ownerClause(alias)` = `(alias.user_id = ? OR (alias.user_id IS NULL AND alias.user_email = ?))` is security-critical: the `IS NULL` guard stops an address one account has moved away from also matching a different account's row. `TeamMembersDAO`, `UserFavoriteAccountsDAO`, and `UserAccessTokenDAO` all delegate to it rather than carrying their own copy (they previously had four, each with its own prose explanation, so a fix to one silently missed the others). DAO methods that take a `null` `userId` narrow to the address arm alone — `ownerClause('')` produces the unaliased two-arm form for that case.

**LIKE metacharacters must be escaped.** `%`, `_`, and `\` in a user-supplied search term are wildcards, so searching for `%` returns every row. Use `LIKEUtil.contains(term)` for the pattern and `LIKEUtil.escapeClause` (`ESCAPE '\'`) in the SQL — `AssumableRolesQueries.buildSearchRolesQuery` and `ResourceInventoryDAO.searchResources` both do.

Conventions: DAOs extend `BaseDAO`/`EncryptedDAO` (never redeclare `database`); failed writes throw `DatabaseError` on `!result.success` (`retryable` flag drives `executeD1WithRetry` backoff); batch deletes expose `deleteOlderThanBatch(cutoff, batchSize): Promise<number>` (D1 `DELETE … LIMIT ?`, `meta.changes ?? 0`) for `AbstractPruningTask`; models use dual camelCase/snake_case `Type`/`TypeInternal` pairs from `@aws-access-bridge/shared/model`. Routes must not import DAOs (ESLint-enforced in `apps/api/src/endpoints/**`, type-only imports excepted) — compose `backend-services` domain services instead.
